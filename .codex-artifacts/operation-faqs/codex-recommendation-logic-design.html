Design document · 2026-06-17 · topik-ai admin + v13 SOT 기준

TOPIK 쓰기 51~54 추천 로직 설계도

이 문서는 관리자 앱의 SOT와 v13 사용자 앱 SOT를 기준으로, MVP에 적용 가능한 규칙 기반 문제 추천 로직을 정의한다. 구현 코드는 포함하지 않으며, 관리자 운영 범위와 v13 소비 흐름 사이의 계약을 맞추는 설계 문서다.

MVP 결정 AI 추천 엔진이 아닌 규칙 기반 다음 행동 선택기
관리자 역할 service_status와 태그로 후보 풀 관리
v13 역할 사용자 이력 기준으로 추천 실행과 상태 저장
후속 범위 약점 엔진, ML, 임베딩 검색은 별도 결정 후 진행

1. 결론

추천 로직은 후보 생성 → 점수화 → 재정렬 → 결과 저장 4단계로 구성한다. MVP에서는 학습자별 AI 분석을 하지 않고, 관리자 메타데이터, v13의 온보딩 목표, 최근 풀이 이력, 기존 추천 실행 기록만 사용한다.

적용 범위

  • TOPIK 쓰기 51~54 문항
  • B-01 홈 추천 카드
  • C-01 문제 유형 추천
  • R-02 피드백 후 다음 문제 추천
  • C-02 문제 목록 fallback

비적용 범위

  • 외부 AI provider 기반 추천
  • 자동 약점 추론 모델
  • 임베딩/유사도 검색
  • collaborative filtering
  • 관리자의 사용자별 추천 row 직접 수정

2. SOT 기준과 해석

구분 확인한 기준 설계 반영
관리자 스키마 경계 topik-ai/docs/architecture/shared-supabase-schema-ownership.md, metadata-tag-schema-transition-decision-record.md 관리자 앱은 topik_writing_* 네임스페이스와 운영 태그, 노출 상태를 소유한다. v13 기존 테이블 DDL은 변경하지 않는다.
문항 운영 계약 admin-data-contract.md, assessment-question-manage-page-ia.md, system-metadata-page-ia.md 물리 노출 상태는 service_status 하나로 본다. 태그 변경과 상태 변경은 RPC와 감사 로그를 거친다.
태그와 추천 키 metadata-tag-schema-rule.md 사실 메타데이터와 운영 태그를 분리한다. recommendation_keys는 점수 가산, avoid_repeat_keys는 반복 회피에 사용한다.
v13 MVP 범위 v13/docs/scope-decisions/2026-06-17-ai-deferred-and-mvp-scope.md, v13/docs/development-core-planning/ 실서비스 AI 기능과 약점 기반 추천 엔진은 보류한다. MVP는 규칙 기반 다음 문제 추천으로 제한한다.
v13 화면 흐름 B-01, C-01, C-02, R-02, X-07 Wireframe 문서 홈, 유형 추천, 피드백 후 다음 추천은 제공한다. X-07 약점 추천은 후속/준비중 또는 R-02 규칙 추천으로 대체한다.
v13 현재 구현 v13/src/lib/practice/next.ts, v13/src/lib/practice/weakness.ts, v13/supabase/migrations/*recommendations.sql recommendation_runs와 recommendation_items는 결과 캐시와 상태 저장으로 사용한다. 현재 fallback 구조를 고도화하되, AI로 포장하지 않는다.

설계상 충돌 회피 원칙: topik_writing_question_recommendation_view 를 v13의 즉시 소비 소스로 고정하지 않는다. v13의 기존 problems 기반 경로와 새 관리자 문항 소스를 모두 ProblemCandidate 어댑터 뒤에 숨기고, 실제 컷오버는 별도 owner 결정으로 처리한다.

3. 멀티 에이전트 조사 합의

검토 역할 핵심 결론 반영 방식
v13 SOT 조사 추천은 51~54 유형, 홈/C-01/R-02 흐름에 존재한다. 다만 AI/약점 엔진은 MVP 보류다. MVP 추천은 규칙 기반으로 제한하고, 약점 화면은 후속 범위로 명시한다.
관리자 SOT 조사 service_status, tag_master, question_tags, topik_writing_question_recommendation_view가 추천 후보 풀 운영의 중심이다. 관리자 화면은 알고리즘 편집기가 아니라 후보 풀 품질 관리 화면으로 둔다.
외부 근거 조사 추천 시스템은 일반적으로 후보 생성, 점수화, 재정렬로 나눌 수 있고, 학습 추천에는 간격 복습과 retrieval practice가 근거가 된다. ML 없이도 동일 구조를 규칙 기반으로 적용하고, 복습 예정 신호를 점수화한다.
비판 검토 사용자별 추천 row를 관리자에게 노출하거나, AI 추천처럼 표현하는 것은 SOT와 개인정보/감사 경계 리스크가 크다. 관리자 조치 로그와 추천 실행 로그를 분리하고, 추천 사유는 규칙 기반 문구로 제한한다.

핵심 분리

관리자 조치

문항의 서비스 노출 가능성, 추천 목적 태그, 반복 방지 태그, 운영주의 태그를 관리한다. 모든 변경은 사유와 감사 로그를 남긴다.

추천 실행

v13에서 사용자별 이력과 목표를 읽어 후보를 선별한다. 관리자 앱은 사용자별 추천 결과를 직접 수정하지 않는다.

결과 소비

추천 결과는 화면 카드와 CTA로 노출하고, 시작/소비 상태만 recommendation_items.status에 반영한다.

5. 후보 데이터 계약

추천 함수는 실제 소스가 관리자 신규 문항 뷰인지, v13 legacy problems 테이블인지 몰라도 되도록 공통 후보 타입만 소비한다.

소스 MVP 처리 전환 조건
topik_writing_question_recommendation_view 관리자 신규 스키마가 준비된 환경의 1순위 후보 소스. service_status='available'만 사용자 추천 후보로 사용한다. v13 소비 컷오버 결정, RLS/읽기 경로, 문항 ID 매핑 검증 완료 후 활성화.
problems legacy source v13 현재 구현과 호환되는 전환기 후보 소스. 공개 상태 문항만 사용하고 추천 키가 없으면 기본 규칙으로 보정한다. 신규 topik writing source가 사용자 앱에서 검증될 때까지 유지한다.

6. 추천 알고리즘

6.1 입력 신호

신호 예시 데이터 MVP 신뢰도
학습 목표 목표 TOPIK 등급, 선호 유형, 목표 난이도, 목표 풀이 수 높음. 온보딩 값 또는 기본값을 사용한다.
최근 풀이 이력 최근 문항, 최근 유형, 제출/완료 시각, 소비한 추천 item 높음. 사용자 소유 데이터이며 규칙 추천의 핵심이다.
피드백 점수 문법, 어휘, 구조, 표현, 주제 적합성 차원 점수 중간. MVP에서는 AI 고도 분석으로 표현하지 않고, 존재하는 점수만 보조 신호로 쓴다.
관리자 문항 메타 유형, 난이도, 주제, 추천 키, 반복 회피 키, 운영 태그 높음. 추천 품질을 좌우하는 운영 입력값이다.
권한/제한 구독, paywall, 제출 가능 횟수, 잠금 상태 높음. 추천 CTA가 실제 시작 가능 상태와 충돌하면 안 된다.

6.2 후보 생성

  1. 현재 화면 context를 정한다: dashboard, type_recommendation, next_problem.
  2. 사용자 목표와 최근 풀이 이력을 읽는다.
  3. 어댑터를 통해 후보 문항을 로드한다.
  4. 문항 유형은 51~54로 제한한다.
  5. 신규 사용자라면 기본값을 적용한다: TOPIK II 3~4 수준, 중간 난이도, 51→52→53→54 순환.

6.3 Hard Filter

필터 규칙 실패 시 처리
노출 상태 신규 소스는 service_status='available', legacy는 공개 상태 문항만 허용한다. 후보 제외
관리자 제외 태그 추천 제외 노출 제외 검수 필요 계열의 활성 태그는 추천 후보에서 제외한다. 후보 제외
운영주의 태그 운영주의 태그가 있는 문항은 primary 추천에서 제외한다. 운영 정책상 허용된 경고성 태그라면 alternative까지만 허용한다. primary 제외 또는 후보 제외
최근 동일 문항 최근 14일 내 풀이한 동일 문항은 primary 추천에서 제외한다. primary 제외, 후보 부족 시 낮은 점수 alternative 허용
반복 회피 키 최근 3개 풀이의 avoid_repeat_keys와 강하게 겹치면 primary에서 제외한다. primary 제외, alternative 감점
접근 가능성 plan/quota/paywall로 바로 시작할 수 없으면 추천 CTA는 paywall 또는 문제 목록 fallback으로 연결한다. 활성 추천 저장 전 차단 또는 paywall CTA

6.4 점수화

점수는 운영자가 화면에서 직접 편집하지 않는다. 초기 MVP에서는 코드 상수와 문서 버전으로 관리하고, 충분한 지표가 쌓인 뒤 별도 정책 카탈로그를 검토한다.

요소 가중치 초안 의도
유형 순환 다음 단계 +20 이력이 적은 사용자는 51→52→53→54 균형 순환
최근 피드백 후 같은 유형 유지 +15 R-02에서 방금 푼 유형의 연습 연속성 유지
목표 레벨/난이도 적합 +12 ~ +15 온보딩 목표와 너무 벗어난 문제 방지
recommendation_keys 일치 +12 관리자/외부 메타데이터가 제시한 추천 목적 반영
대표 문제/학습 흐름 태그 +8 ~ +10 초기 사용자와 방향 없는 사용자의 안정적 시작점 제공
복습 예정 신호 +10 간격 복습과 retrieval practice 반영
미풀이 문항 +10 같은 문항 반복 추천을 줄임
avoid_repeat_keys 최근 겹침 -30 상황/자료/답변 유형 반복 노출 회피
같은 유형 과다 반복 -15 최근 3회 이상 같은 번호만 푸는 흐름 방지
난이도 급상승 -10 목표 난이도보다 2단계 이상 높은 문항 연속 방지
최근 skip/consume -20 방금 넘긴 문제를 즉시 다시 추천하지 않음

6.5 재정렬

  1. 점수 상위 후보를 가져온다.
  2. primary 1개와 alternative 최대 3개를 구성한다.
  3. 가능하면 primary와 alternative의 itemNumber, 주제, 반복 회피 키가 겹치지 않게 한다.
  4. 동점이면 미풀이, 낮은 운영 리스크, 오래 노출되지 않은 문항을 우선한다.
  5. 최종 후보가 없으면 추천 없음 상태를 정상 결과로 반환한다.

6.6 의사 코드

function generateRecommendation(userId, context) {
  const activeRun = findReusableActiveRun(userId, context);
  if (activeRun) return activeRun;

  const signals = loadUserSignals(userId);
  const candidates = loadProblemCandidates(context);
  const filtered = applyHardFilters(candidates, signals, context);
  const scored = filtered.map(candidate => ({
    candidate,
    score: scoreCandidate(candidate, signals, context),
    reasonCodes: buildReasonCodes(candidate, signals, context),
  }));
  const ranked = rerankForDiversity(scored, signals);
  const items = takePrimaryAndAlternatives(ranked);

  if (items.length === 0) {
    return emptyRecommendation("NO_AVAILABLE_CANDIDATE");
  }

  return persistRunAndItems(userId, context, items);
}

8. 저장과 상태 전이

객체 역할 MVP 규칙
recommendation_runs 추천 실행 묶음 source_type='dashboard'는 B-01, source_type='next_problem'은 R-02에 사용한다. C-01은 별도 enum 결정 전에는 transient 계산 또는 dashboard run 재사용을 권장한다.
recommendation_items 추천 후보와 화면 순서 rank, reason, estimated_minutes, weakness_tags, status만 화면 소비에 사용한다. "AI 추천 결과"로 표현하지 않는다.
study_events 노출/클릭/시작/완료 계측 추천 품질 판단은 먼저 이벤트와 완료율을 모은 뒤 한다. 원문 답안, 상세 피드백 본문, 개인정보성 payload는 저장하지 않는다.

만료 정책 초안

  • R-02 다음 문제 추천: 24시간 또는 새 제출/피드백이 생기면 만료
  • B-01 홈 추천: 7일 또는 추천 item이 consumed 되면 재생성
  • C-01 유형 추천: MVP에서는 화면 요청 시 계산하고 별도 저장은 보류
  • skip 상태: 현재 enum에 skipped가 없으므로 MVP에서는 expired 처리 또는 no-op 중 하나를 결정한다.

보안/권한 주의: recommendation_items는 user-owned 데이터다. 관리자 화면에서 개인별 추천 row를 직접 조회하거나 수정하지 않는다. 클라이언트가 status='consumed' 외 컬럼을 바꾸지 못하도록 RLS와 RPC/서버 액션 경계를 검토해야 한다.

9. 관리자 운영 설계

관리자가 조정할 수 있는 것

  • service_status: available, excluded, internal_test
  • 추천 목적 태그: 대표 문제, 복습 적합, 유형 입문, 난이도 계단 등
  • 반복 방지 태그: 같은 상황, 같은 자료형, 같은 답변 패턴 회피
  • 운영주의 태그: 노출 전 경고, 내부 확인 필요, 콘텐츠 민감도
  • 태그 마스터 활성/비활성: /system/metadata에서 권한자만 토글

12. 검증 기준

추천 로직 단위 검증

  • service_status!='available' 문항은 신규 소스 추천에 나오지 않는다.
  • legacy source에서는 공개 상태가 아닌 문항이 나오지 않는다.
  • 추천 제외/노출 제외/검수 필요 계열 태그가 있으면 후보에서 제외된다.
  • 목표와 이력이 없는 신규 사용자는 51→52→53→54 순환을 따른다.
  • 최근 풀이 문항과 같은 avoid_repeat_keys가 primary에 반복되지 않는다.
  • 후보가 없으면 R-02는 empty 문구와 C-02 CTA를 보여준다.

권한/보안 검증

  • 사용자는 본인 recommendation_runs/items만 조회한다.
  • 사용자 클라이언트는 추천 item의 status 외 핵심 필드를 변경할 수 없다.
  • 관리자 화면은 사용자별 추천 row를 직접 노출하지 않는다.
  • 추천 로그에는 원문 답안, 상세 피드백 본문, 개인정보성 payload를 넣지 않는다.
  • 관리자 상태/태그 변경은 RPC, 사유, 감사 로그 링크를 통과한다.

화면 검증

  • B-01, C-01, R-02, C-02에서 loading/empty/success/error/disabled 상태가 구분된다.
  • 추천 사유는 최대 2줄 안에서 규칙 기반 문구로 표시된다.
  • paywall/제출 제한이 있으면 시작 CTA가 잠금 또는 paywall 흐름으로 연결된다.
  • 추천이 없는 상태에서도 사용자는 C-02에서 직접 문제를 선택할 수 있다.

15. 채택할 설계 문장

TOPIK 쓰기 추천은 MVP에서 규칙 기반 다음 문제 선택기로 구현한다. 관리자 앱은 service_status, 활성 태그, 추천 키, 반복 회피 키를 통해 추천 후보 풀을 관리하고, v13은 사용자 목표와 최근 풀이 이력을 기준으로 후보를 점수화해 primary 1개와 alternative 최대 3개를 제시한다. AI provider, 자동 약점 추론, 사용자별 추천 개입, 추천 가중치 관리자 UI는 후속 scope decision 전까지 포함하지 않는다.
