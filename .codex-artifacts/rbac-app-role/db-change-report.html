권한 화면 → 관리자 등급(app_role) 변경 화면 전환 — DB 변경 보고서

2026-06-18 · 브랜치 feat/operation-notices-db · dev DB fglggyfvzjdsbyckinqa · 구현=Codex GPT-5.5, 검증·적용·문서·커밋=Claude

한 줄 요약. 관리자 권한 화면(/system/permissions)을 "구경용 권한 카탈로그"에서 실제로 관리자의 등급(profiles.app_role)을 바꾸는 화면으로 바꿨습니다. 이를 위해 DB에 함수 2개를 추가했고(테이블 변경 0), 가장 민감한 권한 상승 동작이라 16건의 실 DB 검증 + 21개 에이전트 적대적 리뷰를 거쳤습니다.

1. 무엇을 왜 바꿨나 (쉽게)

이 관리자 도구에서 "누가 어떤 권한을 갖는지"의 진짜 기준은 profiles.app_role 한 곳입니다(2026-06-17 RBAC SoT 결정). 화면에 있던 37개 권한·5개 RoleKey 표는 사실 메뉴를 보여줄지 말지를 정하는 표시용일 뿐, 실제 권한을 바꾸지 않았습니다. 그래서 이 화면을 진짜로 등급을 바꿀 수 있는 화면으로 바꿨습니다.

오너가 확정한 5가지 방침:

항목확정
① 변경 방식platform_admin만 다른 관리자의 등급을 바꿀 수 있고, 바꾸면 "이전→새 등급 + 사유"를 감사 로그에 남긴다.
② 승인단독 실행(2인 승인 없음).
③ 반영 시점다음 로그인 때 반영. 강제 로그아웃·토큰 폐기는 하지 않는다.
④ org_admin 매핑org_admin → READ_ONLY 임시 현행 유지.
⑤ 화면 정체성조회용 축소가 아니라 실제 등급 변경 화면으로 개조. 카탈로그는 읽기 전용 참고로 잔존.

2. DB에 추가된 것 함수 +2 · 테이블 0 · 정책 0

무변경 검증: 함수 137 → 139 (정확히 +2), 테이블 61→61, RLS 정책 91→91, 뷰 1→1. 기존 테이블/트리거/정책 일절 변경 없음.

2-1. 쓰기 함수 admin_set_admin_app_role(p_target_user_id, p_new_app_role, p_reason)

관리자의 app_role을 실제로 바꾸는 단 하나의 경로입니다. 마이그레이션 20260618093000_admin_set_app_role.sql.

  • 가드: 미인증 → unauthenticated, platform_admin 아님 → forbidden, 사유 미입력 → reason required, 잘못된 등급 → invalid app_role.
  • 잠금 방지: 자기 자신 platform_admin 강등 차단 + 마지막 platform_admin 강등 차단(혼자 남은 관리자가 스스로를 내려 잠기는 사고 방지).
  • 자기검증 쓰기: UPDATE … RETURNING으로 실제 반영값을 확인 — 혹시라도 v13 보호 트리거가 향후 쓰기를 막으면 거짓 감사 없이 즉시 실패합니다.
  • 감사: admin_audit_logs에 action=admin_role_changed, target=AdminAccount, diff={app_role:{from,to}}, payload={reason,target_email,target_display,session_policy:'next_login'} 기록.

2-2. 조회 함수 admin_list_admin_app_roles(p_search)

화면의 관리자 목록을 읽는 함수입니다. 마이그레이션 20260618094000_admin_list_admin_app_roles.sql. platform_admin 전용, app_role <> 'learner'를 SQL에서 필터해 학습자(다수)가 페이지 한도를 잠식하지 못하게 합니다(아래 리뷰 F3 대응).

2-3. 핵심: v13 소유 컬럼에 어떻게 안전하게 쓰나

profiles는 v13 소유이고, private.protect_profile_columns 트리거가 컬럼을 보호합니다. 트리거 원본을 확인한 결과 관리자(is_admin: content_admin/platform_admin, active)에 대해서는 보호를 전면 우회합니다 — 즉 platform_admin은 app_role을 쓸 수 있습니다. 이는 이미 운영 중인 admin_set_user_status가 status 컬럼을 쓰는 것과 완전히 동일한 메커니즘입니다. v13 DDL/트리거는 한 줄도 바꾸지 않았습니다.
