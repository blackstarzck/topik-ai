## 0. 한눈에 보기 (Executive Summary)

- **무엇을 바꾸나**: ⓑ v13 단일 `problems`(13컬럼) 기반의 현행 admin을, ⓐ 권장안의 **8개 신규 오브젝트** — `topik_writing_51/52/53/54_questions`(번호별 4분리), `topik_writing_tag_master`, `topik_writing_question_tags`, `topik_writing_topic_master`(17주제), `topik_writing_question_recommendation_view` — 기반으로 전면 전환한다.
- **3축 범위**: ① 기능(검수/문항 관리/태그 운영/마스터 관리), ② 테이블 스키마(8개 오브젝트 + 식별자 매핑 테이블 1개 제안), ③ Supabase 세팅(마이그레이션 체계 신설, RLS, 감사 RPC, 시드).
- **순서의 원칙**: 데이터가 먼저 존재해야 화면을 바꿀 수 있다(P1→P2→P3). 읽기와 검수 쓰기는 **같은 컷오버에서 함께** 신규 스키마로 전환한다 — 읽기만 옮기고 쓰기를 구 경로에 남기면 ID 체계 불일치(신규 TEXT `question_id` vs `problems.id` UUID)와 기록 발산이 생기기 때문. 신규 운영 기능(태그·노출 통제)은 P4, 신규 surface는 P5, 상류 연동은 P6 게이트로 분리한다.
- **무손실 백필 전략**: 원본 `answer_key`(JSONB)는 신규 테이블의 공통 `answer_key` 컬럼에 **그대로 보존**하면서 `blank_*` 정규화 컬럼을 병행 생성한다. 필수 컬럼 역분해 실패 문항은 NOT NULL 제약 위반을 피해 **적재 보류**(테이블 미적재, `question_source_map`과 검증 리포트로 추적)로 처리하고 콘텐츠팀 재입력 후 적재한다.
- **호환 전략**: P2(백필) 이후 P3(컷오버) 전까지 구 화면이 `problems`에 계속 기록하므로, 컷오버 직전 **검수 freeze 윈도 + ETL 델타 재적재**로 따라잡고, 컷오버 후 `problems`는 read-only 레거시로 동결한다. v0.8 원안 대비 편차는 §5.2 편차 목록에 전부 명시한다.

## 3. 목표 아키텍처 (To-Be)

### 3.1 데이터 흐름

```
[콘텐츠팀 입력표/90문항 JSON]
        │ (P2 백필 ETL: 채번·역분해·재분류)
        ▼
topik_writing_51/52/53/54_questions  ←─ 공통 컬럼 동일(§7.1 + 편차 1: review_workflow_status)
        │  ├── topik_writing_topic_master (17주제 × 세부, 읽기 참조)
        │  ├── topik_writing_question_tags ⇄ topik_writing_tag_master (운영 태그)
        │  └── topik_writing_question_source_map (제안: problems.id ↔ question_id ↔ published_task_id)
        ▼
topik_writing_question_recommendation_view
  (§7.9 12컬럼 + admin 목록용 확장 컬럼, UNION ALL, security_invoker, 읽기 전용)
        │
        ├── admin 목록 화면(검수/관리): 뷰 조회 + 태그 조인
        ├── admin 상세 화면·쓰기: item_number로 번호별 테이블 직조회/RPC 라우팅
        └── (P6) 상류 Writing API 업로드 → GET /api/writing/tasks 사용자 노출
```

### 3.2 설계 원칙 (v0.8 §6.4 + 현행 거버넌스 계승)

1. **메타데이터(불변 사실)와 태그(가변 운영값)의 물리 분리** — 태그는 문제 테이블 컬럼이 아니라 `question_tags` 매핑으로만 존재한다.
2. **공통 컬럼명 4테이블 동결** — 추천 뷰가 UNION하는 공통 컬럼 집합은 P1 종료 시점에 계약으로 동결하고, 이후 변경은 4테이블 동시 마이그레이션으로만 허용한다(컬럼 drift 방지, 영향도 보고서 §8-11).
3. **읽기=RLS 직조회, 쓰기=감사 RPC 단일 경로** — 현행 `problems` 모델과 동일. 신규 테이블·태그에 대한 직접 write는 RLS로 차단하고, SECURITY DEFINER RPC가 `admin_audit_logs`에 diff를 남긴다(현행 감사 계약과 동등 보장, `docs/specs/admin-data-contract.md` §12.3).
4. **목록=뷰, 상세/쓰기=번호별 테이블** — 뷰는 읽기 전용이므로 상세 재조회와 write는 `item_number`로 대상 테이블을 라우팅한다. `question_id`에 번호가 인코딩되어 있어(`topik-writing-51-0001`) 라우팅은 결정적이다.
5. **원본 보존 우선** — 백필 시 원본 JSONB(`answer_key`)·원본 식별자(`problems.id`)·상류 식별자(`published_task_id`)를 모두 보존해 역추적과 재실행(idempotent)을 보장한다.
6. **읽기·쓰기 동시 컷오버** — 한 화면이 읽는 저장소와 쓰는 저장소를 다르게 두는 기간을 만들지 않는다(P3 원칙).

### 5.3 RLS·RPC 설계

- **읽기 RLS**: 테이블 7종 전부 `content_admin`/`platform_admin` SELECT 허용(현행 `problems` 정책과 동일 모델). 뷰는 RLS가 직접 붙지 않으므로 `security_invoker=true`로 베이스 테이블 RLS를 상속시키고, anon/비관리자 SELECT 차단을 P1 스모크의 네거티브 테스트로 확인. `tag_master`/`topic_master`는 admin 역할 한정.
- **쓰기 차단**: 모든 테이블 직접 INSERT/UPDATE/DELETE는 RLS로 차단. 쓰기는 RPC만:
  - `admin_update_topik_question(question_id, item_number, patch)` — 화이트리스트 키만 허용(`review_status`, `review_workflow_status`, `service_status`, `content_team_memo` 등 가변 컬럼 한정. `review_status='approved'` 전이 시 `review_passed=true` 동기 기록). 메타데이터(불변 사실) 컬럼은 "오류 수정" 모드 키로만 허용할지 P4에서 확정.
  - `admin_assign_question_tag(question_id, item_number, tag_code, tag_value, memo)` / `admin_remove_question_tag(tag_assignment_id, memo)` — `is_active`/`removed_at` 갱신 방식(이력 보존), 감사 기록 동반. '서비스_노출상태' 그룹 부여는 가드로 차단(D-6).
  - 백필 전용 경로: P2 스크립트가 service-role 키로 직접 upsert(일회성, RLS 우회는 service-role 한정) 또는 `admin_backfill_upsert_question` RPC 중 택일.
- **감사 계약**: actor=`auth.uid()`, Target Type=`AssessmentQuestion`, Target ID=`question_id`, 컬럼 diff 기록 — 현행 `admin_update_problem` 보장과 동등(D-8).

### 5.4 프로덕션 적용 게이트 (P1↔P2 사이)

스테이징 검증만으로 P1을 끝내지 않는다. P2(실데이터 적재)·P3(실화면 전환)는 프로덕션 스키마를 전제하므로:

1. v13 팀 승인 증적(경계 합의서 기준) → 2. 프로덕션 마이그레이션 적용 → 3. 프로덕션 스모크(8오브젝트 SELECT + RLS 매트릭스 + 뷰 네거티브 테스트) → 4. **기존 테이블 무변경 diff 확인**(신규 오브젝트만 추가됐음을 증명) → 5. **파일럿 적재 왕복 검증(RT-1, §12.0)**: 번호별 샘플 문항·태그를 실제 적재해 4경로(테이블/뷰/태그 조인/RLS) 조회가 입력과 일치함을 확인.

**P1 완료 조건**: §5.4 게이트 통과(프로덕션 적용 완료 기준). 시드된 마스터 2종 + 문제 테이블 4종 + 뷰가 admin 계정으로 SELECT 가능, anon 차단 확인, RT-1 통과 증적. 완료 판정은 §12.3 P1 채점표로 채점하며, **PASS여야 P2 본 적재 착수 가능**(ETL 스크립트 선행 개발은 §12.3 착수 금지 범위 예외).

## 6. Phase 2 — 데이터 백필 / ETL

### 6.1 입력물

- v13 `problems` 현행 행(51~54) — `legacy_problem_id` 매핑·검수 상태 이관용.

### 6.2 ETL 스크립트 (이 repo `scripts/etl/` 신설, Node + `SUPABASE_SECRET_KEY`)

1. `scripts/etl/extract-problems.mjs` — v13 `problems` 51~54 덤프 + 52/53/54 실재 여부 리포트(D-9 확정 입력).
2. `scripts/etl/transform-questions.mjs` — 채번(D-4: source_map 선조회), 컬럼 매핑(§3.3), `answer_key` 역분해, 재분류 입력표 병합. 산출: 테이블별 upsert payload + 적재 보류 목록 + 검증 리포트.
3. `scripts/etl/load-questions.mjs` — source_map 매핑 기준 idempotent upsert(재실행 안전), `question_source_map` 동시 기록, `auto_checks_passed` 기록.
4. `scripts/etl/verify-backfill.mjs` — §6.3 검증 자동화.

### 6.3 무손실 검증 (D-5)

- **재조립 검증**: `blank_*_canonical_answer`를 `prompt_text`에 삽입해 `resolved_text`와 일치하는지 문항별 비교. 결과를 `auto_checks_passed`에 기록.
- **보존 검증**: 원본 `answer_key` JSONB와 정규화 컬럼의 정답 집합 동치 비교.
- **수량 검증**: `problems` 추출 건수 = 4테이블 적재 건수 + 적재 보류 건수(사유 목록 포함).
- **축 검증**: `topic_main`/`topic_detail`이 `topic_master` 고정값 집합에 전부 포함.
- **왕복 검증(RT-2, §12.0)**: 적재 직후 실제 DB를 재조회(SELECT)해 upsert payload와 필드별 diff 0건 확인 — 변환 산출물이 아니라 **DB에 실제로 저장된 값**을 비교 대상으로 삼는다.

**P2 완료 조건**: 백필 범위 전수(D-9 확정: `problems` 51~54 전수 470행) 중 검증 통과분이 적재되고 검증 리포트 5종 통과(적재 보류분은 재입력 대기 목록으로 산출·발주). 콘텐츠팀이 샘플 검수(예: 10문항)로 승인. **델타 재적재 리허설 1회**(P3 컷오버 절차 검증). 완료 판정은 §12.3 P2 채점표로 채점하며, **PASS여야 P3 컷오버 실행 가능**(P3 코드 선행 개발은 예외, 컷오버 배포는 불가).

## 7. Phase 3 — 읽기·검수 컷오버 (코드 전환의 본체)

읽기와 검수 쓰기(검수 상태·메모)를 **한 컷오버로 함께** 신규 스키마로 전환한다. 읽기만 옮기고 쓰기를 `admin_update_problem`에 남기면: ① 신규 TEXT `question_id`를 UUID 기대 RPC에 전달하게 되고, ② 쓰기 결과가 `problems`에만 남아 화면(신규 테이블)에 반영되지 않으며, ③ 두 저장소의 검수 상태가 영구 발산한다. 따라서 P1에서 RPC를 선행 구축하고 P3에서 읽기·쓰기를 동시에 교체한다.

### 7.1 컷오버 절차

1. **검수 freeze 윈도 선언**(운영 공지, 반나절 내 목표) → 2. ETL 델타 재적재(P2 이후 `problems`에 발생한 변경 따라잡기) → 3. 신·구 발산 0건 대사(`review_status`/`review_workflow_status`/메모 영향 컬럼) → 4. 코드 배포(읽기+쓰기 동시 전환) → 5. `problems` read-only 동결(v13 합의 절차) + 구 읽기 어댑터는 **플래그 봉인으로 P4 종료까지 보존**(롤백 경로, §12.2).

### 7.3 게이트·검증

- `npm run harness:check` + `npm run build` + 변경 영향 e2e(재작성 spec, `list-loading-consistency`).
- 컷오버 절차 §7.1의 3번(발산 0건 대사)을 P3 완료의 필수 증적으로 기록.
- **실데이터 화면 표시 대사(RT-3, §12.0)**: 백필된 실제 문항 샘플(번호별 최소 1건, 권장 10건)의 목록·상세 화면 표시값을 원본 입력표/DB 값과 필드별 대사 — 실제 DB에 쌓인 데이터가 화면에 "제대로 나오는지"를 컷오버 판정 기준으로 삼는다.
- **검수 쓰기 왕복(RT-4)**: 화면에서 검수 상태/메모 write → DB 값 직접 확인 → 화면 재조회 반영 → 감사 로그 역추적 1사이클.
- 문서 동기화(§11): 데이터 계약 §9.6, page-tables #19/#19-1, 양 page-IA 매핑 블록, page-sync §5-7 후보 표.

**P3 완료 조건**: 두 목록 페이지+상세 페이지가 신규 스키마만 읽고, 검수 상태·메모 쓰기가 신규 RPC로 동작하며(감사 로그 역추적 확인), `problems` 경로는 플래그 봉인 상태로만 잔존. 발산 0건 대사 + RT-3/RT-4 증적 + e2e 통과. 완료 판정은 §12.3 P3 채점표로 채점하며, **PASS여야 P4 write 개방 가능**.

## 8. Phase 4 — 운영 쓰기·태그 (신규 능력 개방)

P3에서 검수 쓰기는 이미 전환됐으므로, P4는 **현행에 없던 운영 능력**을 감사 계약과 함께 개방하는 단계다.

| 작업 | 내용 | 해소되는 현행 갭 |
| :---- | :---- | :---- |
| 노출 통제 write | manage 페이지 액션 → `service_status` 갱신(`admin_update_topik_question`). `OPERATION_WRITE_ENABLED` 게이트·facade throw 제거(lifecycle_status 종속 해소 — 신규 스키마가 자체 컬럼 보유) | `OPERATION_WRITE_ENABLED=false` 봉인 해제 |
| 태그 부여/제거 | 상세(또는 manage) 화면에 태그 편집 UI: tag_master 사전 기반 부여/제거 + 사유 memo. 신규 감사 액션 코드(`tag_assigned`/`tag_removed`). 노출상태 그룹 차단 가드(D-6) | net-new |
| 노출 제외 기준 적용 | D-6에서 정한 기준을 `tag_master.usage_rule`·운영 가이드에 반영 | 정책 공백 |
| 감사 표면 갱신 | `system-audit-logs-page.tsx` 액션 라벨 맵에 신규 코드 추가, Target ID=question_id 딥링크 검증 | — |
| 문서 | `docs/specs/admin-action-log.md`에 신규 write 계약(액션·Target·사유·역추적 경로) 추가, POL-017 행 갱신 | — |

**P4 완료 조건**: 모든 write가 RPC 경유로 동작하고 감사 로그에서 역추적 가능. **운영 쓰기·태그 왕복(RT-4, §12.0)**: 화면에서 service_status 변경/태그 부여·제거 → DB 값 확인 → 화면 재반영 → 감사 로그까지 1사이클 증적. 파괴적 액션은 ConfirmAction+사유 입력 유지. RLS 직접 write 차단 재확인. P4 종료 시점에 구 problems 어댑터 플래그 봉인 제거 여부 판단(§12.2). 완료 판정은 §12.3 P4 채점표로 채점하며, **PASS여야 P5 착수 가능**.

## 9. Phase 5 — 마스터 관리·신규 surface (D-10 범위 내)

- **주제/태그 마스터 조회**: 1차로 `/system/metadata` 코드 테이블 페이지에 실데이터 그룹(topic_master, tag_master)으로 노출(현행 모크 그룹 store에 신규 그룹 추가, 또는 Supabase 연동 그룹 신설). 별도 전용 페이지가 필요해지면 신규 라우트 + page-IA 문서 + 메뉴/브레드크럼/권한 키(`assessment.tag-master.manage` 등) 일괄 작업(라우트-IA 하네스 게이트 준수).
- **추천키/반복방지키 편집**: D-10 비범위 원칙상 조회만 제공(JSONB 표시). 편집은 후속 제품 결정.
- **마스터 write**: tag_master 활성/비활성 토글 정도만 admin 허용(platform_admin), 신규 Target Type 결정.
- **53번 자료 자산 저장소 결정 실행**(D-13 후속): Storage 버킷/CDN 채택 시 업로드 경로·`data_asset_url` 채움 정책 확정.

**P5 완료 조건**: 마스터 데이터가 admin에서 조회 가능하고, 신규 라우트가 생겼다면 page-IA·메뉴·권한·감사 문서가 같은 작업에서 동기화됨. 완료 판정은 §12.3 P5 채점표로 채점하며, **PASS여야 P6 상류 연동 실행 가능**(P6는 외부 게이트 D-11 확정도 병행 전제).

## 10. Phase 6 — 상류 배포·노출 연동 (외부 게이트, POL-017)

- 선행: D-11 엔드포인트(업로드 upsert·노출 토글) 상류 확정 + `docs/specs/topik-ai-service-api-reference.md` 스냅샷 재생성.
- 신규 스키마 → `GenerateProblemResponse` 매핑 재정의(기존 §10.3 problems 기준 매핑 대체): `item_number`→task_type(**task52 부재 이슈 해소 필수**), `prompt_text`→instruction, `topic_main` 라벨→topic, `difficulty_level`→easy/medium/hard 밴드, max_score 파생(51/52=10, 53=30, 54=50).
- 배포 액션: 검수 완료 문항의 업로드를 별도 감사 액션(`question_published`)으로 구현, `published_task_id`를 `question_source_map`에 기록(배포 증적).
- 노출 동기화: `service_status` 변경 ↔ 상류 노출 토글 호출 정합(실패 시 보상 정책 포함).

**P6 완료 조건**: 검수 완료 → 업로드 → 사용자 노출 → 노출 제외 왕복이 감사 로그·source_map으로 역추적 가능(POL-017 "코드 반영" 승격, `docs/specs/admin-policy-source-map.md` 갱신). 완료 판정은 §12.3 P6 채점표로 채점하며, **PASS 시 전환 프로젝트 종료 선언**(§12.4 스코어카드 전 페이즈 PASS 확인).

## 12. 검증 계획·롤백 전략

### 12.0 왕복 검증 원칙 (공통 기준)

각 단계의 핵심 검증 기준은 **"실제 Supabase DB에 데이터를 적재하고, 실제 소비 경로(테이블/뷰/RLS/화면)로 다시 꺼냈을 때 입력과 일치하는가"**다. 모크·빈 테이블 스모크·정적 검사 통과만으로는 게이트를 닫지 않는다. 체크포인트 4개:

| 체크포인트 | 단계 | 검증 내용 |
| :---- | :--: | :---- |
| RT-1 파일럿 적재 왕복 | P1 | 번호별 샘플 문항 각 1건 + 태그 부여 1건을 **실제 프로덕션 DB**에 적재(`backfill_batch='pilot'`, `service_status='internal_test'` 표식) → ① 번호별 테이블 직조회 ② 추천 뷰 조회 ③ 태그 조인 ④ admin 역할 RLS 경유 조회 — 4경로 모두 입력값과 필드별 일치 확인 후 파일럿 행 정리(또는 internal_test로 유지) |
| RT-2 본 적재 재조회 | P2 | 본 적재분(D-9 확정: 51~54 전수) 적재 직후 DB를 재조회(SELECT)해 upsert payload와 **필드별 diff 0건** 확인 — `verify-backfill.mjs`가 수행("쌓은 데이터가 그대로 나오는지"를 DB 단에서 증명) |
| RT-3 화면 표시 대사 | P3 | 백필된 실제 문항 샘플(번호별 최소 1건, 권장 10건)에 대해 admin 목록·상세 화면 표시값을 원본 입력표/DB 값과 필드별 대사 — e2e live 모드(D-12 시드 admin 계정) 또는 수동 체크리스트로 증적 기록 |
| RT-4 쓰기 왕복 | P3~P4 | 화면에서 write(검수 상태/메모/태그/service_status) → DB 값 직접 확인 → 화면 재조회 반영 → 감사 로그 역추적까지 한 사이클 검증 |

실DB 왕복 검증은 D-12의 시드 admin 계정(화면 경로) 또는 service-role 스크립트(DB 경로)로 수행한다.

### 12.3 페이즈 게이트 채점 체계 (PASS / CONDITIONAL / FAIL)

모든 페이즈는 완료 시점에 아래 채점표로 **채점**하며, 종합 판정이 **PASS일 때만 다음 페이즈에 착수**할 수 있다.

| 판정 | 의미 | 진행 규칙 |
| :---- | :---- | :---- |
| **PASS** | [필수] 항목 전부 충족 + 항목별 증적 존재 | 다음 페이즈 착수 허용 |
| **CONDITIONAL** | FAIL 항목은 없으나 [필수] 항목 일부가 증적 미비·외부 승인 대기 등 비차단 사유로 미완 | 다음 페이즈 착수 **불가**. 미완 항목별 해소 조건·담당·기한을 §12.4에 기록하고, 해소 후 **재채점으로 PASS 전환해야** 진행 |
| **FAIL** | [필수] 항목 미충족(기준 불충족 또는 증적 부재) | 착수 불가. §12.2 롤백 트리거 검토 → 원인 해소 후 해당 페이즈 재수행·재채점 |

**채점 규칙**

- 항목 단위 판정: 기준 충족+증적=PASS / 핵심은 충족했으나 증적·범위 일부 미비=CONDITIONAL / 미충족=FAIL.
- 페이즈 종합 판정: 항목 중 FAIL이 1건이라도 있으면 FAIL, FAIL 없이 CONDITIONAL이 있으면 CONDITIONAL, 전부 PASS면 PASS. [권장] 항목은 종합 판정에 산입하지 않되, 미충족 시 후속 계획을 §12.4에 기록한다.
- **착수 금지의 범위**: "다음 페이즈 착수"는 비가역 실행(프로덕션 DDL 적용, 실데이터 적재, 컷오버 배포, write 개방, 상류 호출)을 의미한다. 가역적 선행 개발(스크립트·코드·문서 초안)은 §14의 병행 표기에 한해 채점 전에도 진행할 수 있으나, 그 산출물의 실행·배포는 직전 페이즈 PASS 후에만 한다.
- 채점자: 프로젝트 오너(또는 위임 검수자). 결과·증적 링크를 §12.4 스코어카드에 기록하고 페이즈 완료 보고에 사본을 첨부한다.
