## 0. 한눈에 보기 (Executive Summary)

- 현행 시스템에는 이미 두 데이터 모델이 가동 중이다 — **ⓑ v13 `problems` 단일 테이블**(13컬럼, 검수 원본 SoT)과 **ⓒ 상류 TalkPik Writing API**(사용자 노출본). 문서는 여기에 **ⓐ 번호별 4분리 테이블 + 태그/주제 마스터 + 추천 뷰(~50컬럼)** 라는 세 번째 모델을 추가하려는 것이다.
- 따라서 핵심 충돌은 컬럼 매핑이 아니라, **"v13이 데이터 주인이고 admin은 거기에 reconcile만 한다"**는 현행 대원칙(`supabase-assessment-question-bank-service.ts` 주석: *"v13 is the schema SoT; topik-ai reconciles TO it"*)과 정면으로 부딪친다는 점이다.
- ⚠️ **중요 전제:** 대상 문서는 **아직 어떤 admin 전환 계약에도 채택되지 않은 standalone 권장안**이며 호스트 주체(v13 vs admin)도 미지정이다. "전환해야 한다"는 것은 결정된 사실이 아니라 **열린 가정**이다.
- 적대적 검증으로 굳건히 확인된 두 명제: ① 문서의 **추천 엔진·태그 시스템은 현행 코드에 소비처가 0건인 net-new** 기능 구축이다. ② 콘텐츠 메타 입력·태그 부여는 현행 사양의 범위(검수 중심)를 벗어난다.

## 1. 배경 — 문서와 프로젝트의 현재 관계

`docs/metadata-tag-schema-rule.md`는 콘텐츠팀이 "검수 완료 90문항 JSON"을 기준으로 **개발팀에 전달하는 권장 데이터 모델·계약서(handoff spec)**이며, 현행 구현의 기술서가 아니다. 코드의 실제 SoT는 문서 스키마가 아니라 v13 백엔드의 단일 `problems` 테이블이다.

| 구분 | 문서 (`metadata-tag-schema-rule.md`) | 실제 프로젝트 (topik-ai-admin) |
| :---- | :---- | :---- |
| 성격 | 콘텐츠팀→개발팀 권장 스키마·계약 (v0.8) | v13에 read-first로 연결된 관리자 어댑터 (Phase C) |
| 테이블 구조 | 번호별 4개 분리 테이블 + 태그/주제 마스터 + 추천 뷰 | 단일 `problems` 테이블을 `question_no in (51,52,53,54)`로 필터 |
| 데이터 주인 | (제안, 호스트 미지정) | **v13** (admin은 데이터 모양을 정하지 않음) |
| 거버넌스 | git untracked, README 미등록 (현재 harness:check FAIL 유발) | — |

문서의 핵심 식별자(`topik_writing_5x_questions`, `topic_main`, `item_number`, `blank_count`, `essay_type`, `tag_master` 등)는 전체 `.ts/.tsx`에서 grep 0건, `.sql` 파일도 0개로 **코드에 한 줄도 결선되어 있지 않다.** 동명으로 살아있는 것은 `review_status`, `answer_key`, `rubric` 정도이고, `item_number→question_no`, `topic_main→topic_category_code`(다른 축), `service_status→operationStatus`(비활성)는 이름·구조가 다르게 재설계된 상태다.

> 근거: `src/features/assessment/api/supabase-assessment-question-bank-service.ts:174-178` (`.from('problems')...`), 같은 파일 `:13-15`(원칙 주석), `:166-168`(읽는 컬럼 13개).

## 2. 핵심 발견 — 마이그레이션이 아니라 제3 모델 신설

문서가 요구하는 목표 구조는 PostgreSQL 기준 **8개 신규 오브젝트**다.

- 번호별 4개 분리 문제테이블 `topik_writing_51/52/53/54_questions` (공통 ~38컬럼 + 번호별 전용 16~22컬럼)
- 태그 마스터 `topik_writing_tag_master` + 문제-태그 매핑 `topik_writing_question_tags`
- 주제 마스터 `topik_writing_topic_master` (17개 고정 주제)
- 추천 검색용 읽기전용 UNION 뷰 `topik_writing_question_recommendation_view`

추천키(`recommendation_keys`)/반복방지키(`avoid_repeat_keys`), 메타데이터 vs 태그 물리 분리, `question_id` 전역 TEXT PK 등은 현행 `problems`에 **source 자체가 없어 백필 즉시 NULL이 되는 신설 축**이다. 즉 단순 스키마 매핑(마이그레이션)이 아니라 새 데이터 제품을 짓는 일이다.

## 3. 소유권 포크 — 진행 전 반드시 택일 (영향도를 가르는 단일 결정)

| | 시나리오 A — v13 소유 | 시나리오 B — admin 별도 소유 | 제3안 — split |
| :---- | :---- | :---- | :---- |
| 구조 | v13이 4테이블+마스터+뷰 신설·소유, admin은 read-first 유지 | admin이 `problems` 밖 별도 스키마 소유 | 메타데이터=v13 / 태그·`service_status`=admin |
| 현행 원칙 정합 | ✅ "v13=SoT" 유지 (이중 SoT 회피) | ❌ 데이터 주인 원칙 붕괴 → 영구 이중 SoT | ⚠️ 무결성 경계 재정의 필요 |
| admin 코드 공수 | L (어댑터/타입/RPC 재작성) | XL + 이중 SoT 운영부채 | 중간 |
| 치명적 단점 | admin이 DDL 권한 없음 → 일정이 외부팀에 종속(리드타임 XL), v13 단일테이블 철학과 충돌 | admin을 사실상 콘텐츠 저작 시스템으로 승격 → 제품 범위 위반 | split도 경계 무결성 새로 정의 |

**권고:** 현행 "v13 reconcile" 원칙을 유지한다면 **A가 정합적**이다. A의 외부 종속을 감내하기 어렵다면 split을 명시적으로 검토해야 한다. **B는 정합성 회귀가 구조적으로 고착되므로 가장 위험하다.**

## 5. 핵심 리스크 (severity 순)

1. 🔴 **이중 SoT 고착** — 소유권 미해결 채 양측이 각자 스키마를 만들면 v13 `problems`와 문서 스키마가 영구 이중 SoT가 되어 정합성 회귀가 구조적으로 고착된다.
2. 🔴 **제품 범위 위반** — 추천키/태그/콘텐츠 메타 입력은 현행 사양 범위(검수 중심)를 벗어나 admin을 콘텐츠 저작 플랫폼으로 확장시킨다.
3. 🔴 **백필 정답 손실** — `answer_key`(JSONB 단일) → `blank_*` 다수 컬럼 역분해의 무손실 보장이 어렵다.
4. 🔴 **"결정됨" 오인** — standalone 권장안을 채택 확정으로 착각하고 착수하면 합의 단계에서 전부 되감긴다.
5. 🟡 **주제 축 불일치** — `topic_category_code`(8값 SUBJECT 축) ↔ `topic_main`(17주제 축) 자동 매핑 불가 → 콘텐츠팀 수작업 재분류 의존.
6. 🟡 *(가정)* 추천뷰 4-way UNION 단일 실패점 / 53번 자료자산(`source_data`/`data_asset_url`) 저장·CDN 동반 신설.

## 6. 차단요인·선결조건 (이게 풀려야 착수 가능)

- **[0순위] 데이터 모델 소유권 결정** (A / B / split) — 안 풀리면 어떤 DDL·마이그레이션·어댑터 재작성도 시작 불가.
- **문서 채택 결정 + 호스트 주체 지정** — 모든 후속의 진짜 0번 선결.
- **v13 `lifecycle_status` 미도착** → `service_status`(노출)를 채울 source 자체가 없음, `OPERATION_WRITE_ENABLED` 게이트 종속.
- **상류 작문 과제 생성/upsert 엔드포인트 미확정** (`docs/architecture/admin-data-source-transition.md:266`) → 신스키마→Writing 매핑·`publishedTaskId` 역추적 불가.
- **topic 축 재분류**(콘텐츠팀), **`question_id` 채번 규칙**, **신규 테이블 감사 RPC 설계**.
- **52/53/54 데이터 실재 여부 확인** (검수 완료 데이터가 51번 중심).

## 7. 권장 단계화 (차단요인을 존중하는 현실적 순서)

| Phase | 목표 | 핵심 포함 |
| :---- | :---- | :---- |
| **Phase 0 — 결정·합의 (코드 0줄)** | 진행 가능 여부·경로 확정 | 소유권 A/B/split 택일, 문서 채택·호스트 지정, 범위 확장 여부, topic 축 전략, `question_id` 규칙, `answer_key` 분해 가능성 판정, §6 콘텐츠팀 값사전 착수 |
| **Phase 1 — 스키마·백필 (소유팀 주도)** | 모델 ⓐ를 실제 DB로 존재시키고 51번부터 무손실 백필 | 8개 오브젝트 DDL, 감사 RPC, `topic_master`+재분류, 90문항 idempotent upsert, `answer_key` 역분해 검증. 52/53/54는 보류/빈 테이블 |
| **Phase 2 — read 어댑터·모델 전환 (admin, lifecycle 무관)** | 노출 write 안 건드리고 read만 신스키마로 | `AssessmentQuestion` 확장, 번호별 분기 select+뷰 조회, `mapRow` 4분기+태그 조인, `mapDomain` 17주제 교체, `REVIEW_STATUS_MAP` 재작성. write는 기존 검수 RPC만 |
| **Phase 3 — 검수/태그 write (범위 결정 후)** | 비목표 해제 승인 범위에 한해 가변값 write 활성화 | 태그 부여/제거, 추천키 편집, 메타 PATCH — 모두 신규 감사계약 준수. 미해제 시 별도 저작도구로 이관 |
| **Phase 4 — service_status·상류 노출 연동 (게이트 종속)** | 노출 통제·배포 마감 | `lifecycle_status` 도착 후 `OPERATION_WRITE_ENABLED` un-stub, 상류 upsert/노출토글 확정, 4테이블→Writing 매핑·POL-017 정합. 53 자료자산은 별도 트랙 |

## 8. 진행 전 반드시 결정할 것 (Phase 0 체크리스트)

1. **[최우선]** 데이터 모델 소유권: A / B / split
2. 문서 채택 여부 + 전환 계약 동기화 책임자
3. 콘텐츠 메타·태그 입력 UI를 admin이 신설할지(범위 확장) vs 별도 저작 도구로 둘지
4. topic 축: `topic_category_code` 유지 / 17주제 전환 / 병존+매핑테이블
5. `review_status` 값: v13 ASCII enum(`approved/rejected`) 유지 / 문서 한국어값 전환
6. `question_id` 채번 권한·규칙, `problems.id` 매핑 위치, 백필 idempotent upsert 키
7. `answer_key`→`blank_*` 무손실 분해 가능 여부 (불가 시 콘텐츠팀 재입력 범위)
8. 신규 테이블/태그 write의 감사 계약(admin-action-log) 충족 방식
9. 52/53/54 데이터 미존재 구간 처리 (빈 테이블 가동 vs 데이터 확보 후 가동)
10. 상류 작문 과제 생성/upsert 엔드포인트 신설 주체·계약, `service_status`↔상류 노출 동기화 정책(POL-017 정합)
11. 4테이블 공통컬럼 drift 방지 거버넌스 (추천 뷰 컬럼 계약 동결 시점·변경 게이트 주체)

## 9. 공수 요약과 분석의 한계 (정직성 단서)

**공수:** 전체 **XL**. 단 XL의 무게중심은 admin 코드가 아니라 **소유권 결정 + 외부 2개팀(v13/상류) 합의 + 콘텐츠팀 값사전·재라벨링 조율**에 있다. 90문항 백필도 `answer_key` 역분해·topic 축 재분류·52/53/54 결측으로 단순 ETL이 아닌 콘텐츠 재가공을 동반한다. **어느 경로든 Phase 0 완료 전 실착수 가능 공수는 사실상 0이며, 현재 admin 측 착수 산출물은 0(`.sql` 0개, 식별자 grep 0건)이다.**

**검증으로 톤을 낮춘 사실(과장 금지):**
- 대상 문서는 standalone v0.8 권장안으로, "전환"은 아직 누구도 결정하지 않은 열린 가정이다.
- 현행 admin은 "검수 자동화"가 아니라 **운영자 주도 수동 검수**(상태 전환 + UI-local 메모)다.
- 현행 비목표 문구는 "문항을 수동 **생성**하지 않는다"로 '생성'만 명시하며, 문서가 admin 내 편집 UI 구축을 직접 요구하지는 않는다(콘텐츠팀 입력표가 산출물). 다만 메타/태그 write가 현행 범위 밖이라는 취지는 유효하다.

**미입증 가정(설계 추정, 사실 단정 아님):** ① 53번 자료자산 CDN "XL", ② 추천 뷰 4-way UNION 성능 리스크, ③ 52/53/54 데이터가 `problems`에 실재하는지 여부. 산정 시 가정으로 표시해 반영해야 한다.
