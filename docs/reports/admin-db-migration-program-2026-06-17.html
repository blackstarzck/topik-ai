결론 한 줄: 관리자가 다루는 운영 데이터(공지·FAQ·이벤트·정책·커뮤니티·포인트·쿠폰·환불·회원·메타데이터·시스템 로그)가 이제 실제 DB에 저장되고, 누가 무엇을 왜 바꿨는지 감사 로그로 추적됩니다. 기존 서비스 데이터는 한 건도 건드리지 않았습니다.

2. 무슨 문제를 풀었나 (쉽게)

관리자 화면은 동작하는 것처럼 보였지만, 내부적으로는 브라우저 메모리 안의 임시 가짜 데이터로 돌고 있었습니다. 그래서:

  • 새로고침하면 사라졌습니다. 공지를 숨기거나 포인트를 조정해도 화면을 새로 열면 원래대로 돌아왔습니다.
  • "누가 무엇을 했는지" 기록이 없었습니다. 조치는 했다고 표시되는데 실제 감사 로그에는 남지 않았습니다.
  • 일부는 표시만 그럴듯하고 실제로는 아무 일도 안 했습니다. (예: 신고 "처리 완료"인데 글은 그대로 노출)
이번 작업은 각 화면을 실제 데이터베이스 테이블 + 안전한 저장 절차(RPC)에 연결해, 변경이 영구 저장되고 감사 로그로 추적되도록 만든 것입니다.

3. 어떻게 안전하게 했나 — "조립 라인"

도메인마다 똑같은 안전 절차를 거쳤습니다. 한 단계라도 실패하면 멈추고 고쳤습니다.

1
설계·구현 (GPT-5.5) — 화면이 쓰던 가짜 데이터의 모양을 그대로 본떠 DB 테이블·저장 절차(RPC)·전환 코드를 GPT-5.5가 작성.
2
dev DB 적용 (Claude) — 마이그레이션을 실제 개발 DB에 적용. (되돌리기용 down 스크립트도 항상 같이 작성)
3
"기존 것 안 건드림" 검증 — 적용 전/후 스키마를 비교해 새로 추가된 것만 있고 기존 객체 변경은 0건임을 매번 확인.
4
계약 일치 검증 — 화면 코드가 기대하는 컬럼 ↔ 실제 테이블 컬럼이 100% 일치하는지 확인(불일치 시 런타임 오류).
5
자동 검사 — 타입체크·린트·E2E 테스트·문서 정합성 검사(harness) 모두 통과.
6
문서 동기화 — 소유권·데이터 계약·감사 계약·페이지 문서 등 SoT 문서를 같은 작업에서 갱신(AGENTS.md 규칙).
7
커밋 + 변경 보고서(HTML) — 도메인별로 무엇이 추가/변경됐는지 보고서 생성 후 커밋.

안전 원칙: 되돌릴 수 없는 단계(DB 적용·커밋)는 사람(Claude)이 직접 통제. v13(사용자 앱) 소유 테이블은 DDL을 바꾸지 않고 읽기/느슨참조만. 쓰기는 항상 사유(reason)를 받는 RPC 한 경로로만.

5. 발견·정합화한 핵심 결함 3가지

① 신고 "처리 완료"인데 아무 일도 안 함 (커뮤니티)
이전: 신고를 처리해도 신고 상태만 "완료"로 바뀌고 대상 글은 그대로 노출, 사용자도 그대로였습니다. 토스트는 "완료"라고 표시.
지금: 처리 시 실제로 글을 숨기고(hide_post) 조치 종류·사유를 감사에 남깁니다. (사용자 정지는 사용자 앱 소유라 의도만 기록·후속) — 시드로 동작 확인 완료.
② 포인트 잔액을 브라우저가 계산 (커머스 — 금전성)
이전: 포인트 수동 조정 시 잔액을 화면(브라우저)이 계산해 보냈습니다. 금전 자산인데 동시성·조작 위험.
지금: 서버에서 사용자별 잠금(advisory lock) + 최신 원장 잠금으로 잔액 계산, 음수 잔액은 DB 제약으로 차단. 브라우저 계산 제거.
③ 환불 승인/거절이 막혀 있었음 (커머스)
이전: 실 DB 연결 시 환불 승인/거절 버튼이 비활성이었고, 환불은 결제 기록에서 "환불됨"을 읽어 항상 "승인"으로만 보였습니다.
지금: 처리 대기/승인/거절 워크플로 테이블을 만들고 승인/거절을 열었습니다. (실제 결제 환불 집행은 사용자 앱 소유라 의도만 기록·후속)
+ 회원 목록 404 — /users가 "함수를 찾을 수 없음"으로 깨져 있었습니다. 화면이 호출하는 조회·정지 함수가 DB에 없던 것. 함수를 추가해 해결(18d872b).

6. 데이터 안전 — 무엇을 보장했나

원칙내용
기존 데이터 무손상매 적용마다 스키마 전/후 비교 → 추가만, 변경/삭제 0건 확인
사용자 앱(v13) 경계v13 소유 테이블(`profiles`·`payment_history` 등)은 DDL 변경 금지, 읽기/느슨참조만
쓰기 단일 경로모든 쓰기는 사유 필수 RPC 한 경로로만(직접 테이블 쓰기 차단, RLS는 관리자 읽기만 허용)
감사 추적모든 조치를 `admin_audit_logs`에 대상 유형·대상 ID·사유·변경 내역(diff)으로 기록 + 화면 역추적 링크
한글 라벨 유지저장값은 코드(ASCII), 화면 표기는 한글 — 매핑 분리

7. 이번에 추가로 반영한 결정 3건

위임 ① 권한(RBAC) SoT 결정을 GPT-5.5에 위임

관리자 권한 화면의 권한 카탈로그와 실제 인가 기준(profiles.app_role)이 어긋나는 문제의 SoT(기준)를 무엇으로 할지를 GPT-5.5가 코드 근거로 분석·결정하도록 위임했습니다. (결정 결과는 권한 관련 SoT 문서에 기록 — 이 보고서 시점 진행/반영 중)

정정 ② admin_audit_logs 소유권 정정 → 감사 화면 길 열림

감사 로그 테이블을 v13(사용자 앱) 소유로 보던 것을 관리자(topik-ai) 소유로 정정했습니다(도메인 기준). 이로써 관리자가 이 테이블에 조회 인덱스·읽기 경로를 추가할 수 있게 되어, 그동안 막혀있던 "감사 로그 화면을 실제 로그에 연결"(Phase 0) 작업의 제약이 풀렸습니다. (소유권 SoT 문서 정정 완료)

보류 ③ 콘텐츠/신규 기획 도메인 보류

아직 화면·기획이 없는 placeholder 도메인(콘텐츠 라이브러리·배지·단어장·소나기·객관식·미션, EPS TOPIK, 레벨 테스트, 이커머스 상품, 챗봇)은 기획 계약 선결이 필요해 이번엔 보류합니다.
