TOPIK 쓰기 문항 은행 — 외부 API 적재 플로우 실행계획안

대상: /assessment/question-bank · 소스: GET /api/writing/tasks · 멀티에이전트 적대 검증(5 렌즈 × 비평 + 종합, 11 에이전트) 종합
부분적으로 논리적 · 현재 빌드에선 구조적 불가

제안한 흐름의 직관(가져오기 → 분류 → 관리 단계로 승격)은 타당합니다. 그러나 4단계 중 2단계가 지금 시스템에서 실행 불가능하고, 1단계는 데이터 모순 위에 서 있습니다. 가장 중요한 교정 한 가지: 목록 → 관리를 행(row)의 물리적 "이동"으로 모델링하지 마세요. 이동시킬 필드 자체가 없습니다(두 페이지가 동일 훅·동일 뷰를 읽고 전체 행을 표시 / service_status는 키가 될 수 없음 — 적재 기본값이자 "노출 해제" 타깃이라 핑퐁 발생). 하나의 인벤토리 + 상태 필터 탭(미관리/관리중)으로 모델링하세요.

⚠️ 결정적 모순 — 이 API로는 "사용자에게 노출"까지 갈 수 없다

사용자 제안 2단계("사용자가 볼 수 있는 상태로 된다")는 이 API에서는 불가능합니다. 코드/문서로 검증한 세 사실이 상호 배타적입니다:

1
이 API(/api/writing/tasks, 학습자 렌더 형태)는 정답 키를 주지 않는다. 응답에 blanks는 라벨(㉠/㉡)뿐 — canonical_answer·모범답안 필드 없음.
2
§7 스키마는 모든 행에 blank_1/2_canonical_answer(정답 키)를 NOT NULL로 요구한다. 정답 없이는 INSERT 자체가 거부됨.
3
인바운드 모델 §0은 관리자의 콘텐츠 저작을 금지한다(검수 개념 삭제). 관리자가 정답을 "직접 입력"하는 보강 화면 = 삭제한 검수 부활.
① 정답 없음 × ② 정답 필수 × ③ 저작 금지 → 동시 성립 불가

즉: 이 API로 가져와 저장·내부 열람까지는 가능하지만, service_status='available'(사용자 노출)에는 도달할 수 없습니다 — 오너가 셋 중 하나를 풀어야 함. 전제 조치: 라이브 응답을 먼저 캡처해 정답 키 포함 여부를 확인(스웨거가 자체 모순). 포함돼 있으면 순수 자동매핑이 가능해져 모순이 해소됩니다.

제안 단계현재 빌드의 현실판정

4 · UX 개선점

  • 가져오기 = 배치 모달 1개(목록에서 실행): task_type(51/53/54) + topic + 건수(기본 ~50). 부제 "supply API에서 가져와 내부 테스트로 저장 — 사용자 비노출"로 라이브 안 됨을 명시.
  • 적재 결과 패널: "추가 N / 중복 건너뜀 M / 적재 보류 K" 각 펼침. 보류는 보류 리스트로, 중복은 기존 행으로 딥링크. (현재는 해피패스만 있어 "왜 안 떴는지" 표시처가 없음.)
  • 일괄 노출 설정으로 "N모달-N사유" 마찰 제거: manage에 체크박스 열(rowSelection — 신규 배선) + "선택 노출 설정" 1회. 정상군은 공유 사유 1개, 운영주의 태그 항목은 개별 확인으로 분기. 서버 RPC가 공유 사유를 문항당 감사 1행으로 팬아웃.
  • "관리로 이동" 느낌은 네비게이션으로: 적재 후 CTA가 manage의 미관리 탭으로 이동. 행은 목록에서 사라지지 않아 재탐색 항상 가능.
  • 생애주기 탭(미관리/관리중/봉인 레거시)을 manage에 추가, 기존 요약카드+필터 패턴 재사용. manage 요약 카운트를 탭 합 = 전체가 되도록 정합화(현재 null service_status 레거시 행은 어떤 카드/탭에도 안 잡히는 사각지대).
  • 얇은 행은 "메타데이터 보강 필요" 배지로 1급 상태 표시(깨진 문항처럼 보이지 않게), service_status에 종속(보강 필요 = 항상 internal_test). task id 형식·난이도 1~10·52번 부재 등 불일치는 보류/보강 상태로 흡수하고 본 목록 컬럼을 깨뜨리지 않음.

6 · 오너 결정 필요

  1. 결정적: 이 API(학습자 렌더)는 정답 키를 안 주는데 §7는 정답 NOT NULL, §0은 저작 금지 — 셋은 상호 배타. 택일: (A) 이 API = 메타/프리뷰 피드, 적재 행은 internal_test로만 존재하고 별도 파이프라인이 완전 행 공급(사용자 플로우는 "저장+내부 열람"까지만 정직). (B) §0 완화 — 범위 한정·감사되는 보강/저작 surface 재도입(= 새 이름의 검수 부활). → 결정 전 라이브 응답에서 정답 키 유무 확인. 있으면 순수 자동매핑으로 모순 해소.
  2. 목록/관리 구분을 하나의 인벤토리 위 상태 필터로 수용 가능? 아니면 행이 물리적으로 이동하는 2페이지를 반드시 원함? → 아키텍처는 필터를 강력 권고. 빌드 전 확정 필요.
  3. 일괄 노출에 배치 공유 사유 1개가 감사/POL-018상 수용 가능? 아니면 운영주의 항목은 항상 개별 사유? → 정상=공유 사유, 운영주의=강제 개별 사유 권고.
  4. 적재 권한은 content_admin 유지(권고) vs platform_admin 승격? 승격 시 별도 권한키? → content_admin 유지 권고(기존 모든 문항 RPC와 일치).
