## 1. 목적

사용자가 설정한 알림 선호(채널·주기·시간)에 따라 실제 알림이 **발송**되고, 사용자는 **인앱 알림센터와 홈 대시보드 알림 카드**에서 알림을 수신·확인하며, 관리자는 **템플릿·대상 그룹·발송 실행·전달 결과**를 운영 화면에서 관리할 수 있는 end-to-end 알림 파이프라인을 구축한다.

현재는 "설정 저장"만 가능하고 "발송"이 없는 상태다. 이 계획은 그 간극을 단계적으로 메우며, **각 단계는 검증 게이트(§8)를 통과해야 종료된다.**

### 2.3 구조적 사실과 SoT 제약

- 두 앱은 **하나의 Supabase 프로젝트를 공유**한다(환경별 분리). v13에 admin RPC가 이미 존재하고 `admin_audit_logs` 공유가 결정돼 있다.
- **스키마 소유권 SoT가 현재 계획을 막고 있다 (선행 개정 필요)**:
  - v13 `AGENTS.md` 비협상 규칙: "admin-oriented schema/migration 추가도 금지" — 관리자용 템플릿/그룹/발송 테이블을 v13에 둘 수 없다.
  - topik-ai `AGENTS.md`: 이 repo의 스키마 소유는 `topik_writing_*` 네임스페이스로 한정, "기존 v13 테이블 DDL 변경은 금지" — 알림 운영 테이블은 현재 범위 밖이다.
  - 따라서 **Phase 0에서 소유권 SoT 개정이 다른 모든 스키마 작업의 선행 조건**이다 (§5.0).
- 관리자 message 기능의 채널(`mail`/`push`)과 사용자 설정의 채널(`email`/`zalo`)이 불일치한다. 인앱 채널은 양쪽 모두 없다.
- 사용자 화면 기준 발송 대상 산정 정보는 이미 충분하다: `channels` + `reminder_time/days` + `timezone` + `notification_prefs`가 모두 저장되고 있다.
- topik-ai와 v13 모두 이 개발 환경에 Docker/Supabase CLI가 없다 — **`supabase db reset`은 검증 기준으로 쓸 수 없다** (§8).

## 3. 일반적인 알림 관리 패턴 조사 요약

### 3.1 파이프라인 구조

```
트리거(이벤트/스케줄/관리자 수동)
  → 대상 산정 + 선호 평가 (opt-in, 채널 선택, quiet hours, 빈도 제한)
  → 템플릿 렌더링 (변수 치환, 다국어)
  → 채널 라우팅 (인앱 / 이메일 / 푸시 / 메신저, 실패 시 fallback)
  → provider 발송 (큐 기반, 재시도 + dead letter)
  → 발송 로그 기록 (idempotency key로 중복 발송 방지)
```

- 발송 전 매번 사용자 선호를 조회해 **채널·주제·빈도 opt-out을 강제**하는 것이 알림 피로 방지의 핵심이다.
- 큐/워커로 트리거와 발송을 분리하고, 재시도·중복 방지(idempotency)·실패 기록을 발송 계층의 기본 요건으로 둔다.
- 발송 이력은 **발송 실행(dispatch/campaign) 단위**와 **수신자×채널 전달 시도(delivery attempt) 단위**의 2계층으로 관리하는 것이 표준이다.

### 3.2 사용자 측 표준 UI

- **Preference center**: 채널 × 알림 유형 매트릭스, 주기/시간 설정 → X-09가 이미 이 형태다.
- **인앱 알림센터**: 헤더 벨 아이콘 + 미읽음 뱃지 + 드롭다운/페이지 수신함. 최신순 정렬, 읽음/전체 읽음, 읽음·미읽음의 시각적 구분. 뱃지는 "수신함에서 읽음 처리가 가능할 때만" 카운트를 노출하는 것이 권장 패턴이다.

### 3.3 관리자 측 표준 구성

- **템플릿 관리**: template_key 단위, 변수, 상태(활성·비활성·초안), 다국어 본문, **알림 분류(class) 지정**.
- **대상(segment) 관리**: 정적 그룹 + 조건 기반 그룹 → message 기능의 groups가 이미 이 형태다.
- **발송 운영**: 즉시/예약 발송, 테스트 발송, 발송 실행 목록 + 수신자별 전달 결과(성공/실패/제외 사유), 재시도.
- **감사**: 발송·상태 변경·선호 우회(bypass)에 사유 기록 + 감사 로그 연동.

## 4. Talkpik 알림 유형·분류 정의와 스키마 영향 분석

### 4.1 알림 분류(class)와 opt-out 정책

알림 유형마다 opt-out 정책이 다르므로, 유형(template_key) 위에 **분류(class)** 를 둔다. 템플릿 생성 시 class 지정은 필수다.

```ts
type NotificationClass =
  | 'transactional' // 계정·결제·보안 등 필수 시스템 알림 — opt-out 대상 아님
  | 'operational'   // 서비스 운영 공지, 시험 일정 중요 변경 — 중요도에 따라 in_app 강제 가능
  | 'learning'      // 학습 리마인더, 주간 요약 — 사용자가 끄면 발송 금지
  | 'marketing'     // 이벤트, 프로모션 — 명시적 동의 없으면 절대 발송 금지
```

| class | opt-out 정책 | 강제 발송(mandatory) |
| --- | --- | --- |
| `transactional` | preference 우회 가능 | 항상. 단 bypass가 감사 로그에 남는다 |
| `operational` | 기본은 pref 존중 | `mandatory=true` 템플릿만 in_app 강제 가능. email/push 강제는 불가. 설정 시 사유 입력+확인 단계 필수 |
| `learning` | **절대 존중** — off면 발송 금지 | 불가 |
| `marketing` | **명시적 동의 없으면 발송 금지** | **`mandatory=true` 저장 자체를 차단** |

- opt-out으로 제외된 수신자는 "발송 안 함"이 아니라 **`skipped`/`opted_out` 상태로 집계**된다 — 관리자 이력에서 제외 사유가 보여야 한다.
- 이 정책으로 기존 rev2의 모순("opt-out이면 어떤 경로로도 미발송" vs "공지는 인앱 강제")을 해소한다: 전자는 learning/marketing/비필수 operational에 적용되고, 후자는 mandatory operational/transactional에만 감사 기록과 함께 허용된다.

### 4.3 기존 테이블 스키마 영향 분석

| 객체 | 새 유형 수용 가능? | 필요한 변경 | DB migration |
| --- | --- | --- | --- |
| `profiles.notification_prefs` | 가능 — 키 화이트리스트는 코드 | 코드 화이트리스트 확장 + X-09 토글 확장 | **불필요** |
| `notification_settings.channels` | 가능 — 제약은 object 타입 체크 | 코드에서 `in_app` 키 추가, missing=true 해석 | **불필요** |

| `notification_log` | **admin 이력 SoT로 부적합** — 사용자별 전달 로그 수준이고, 발송 실행(dispatch) 개념·제외 사유·집계 상태가 없다 | **변경하지 않는다.** 발송 이력 SoT는 신규 2계층(§5.2)이 담당. notification_log는 deprecated 봉인 + X-09 이력 패널의 데이터 소스를 교체 (O-9) | **불필요** (rev2의 dedupe_key 추가안 철회) |

## 5. 목표 아키텍처

### 5.0 스키마 소유권 (선행 SoT 개정)

공유 Supabase 프로젝트의 스키마 소유권을 **앱 기준이 아니라 도메인 기준**으로 재정의한다.

- **v13 소유**: B2C 사용자 경험에 직접 필요한 core user-facing schema — `user_notifications`(인앱 수신함), 마케팅 동의 저장소, 기존 `profiles`/`notification_settings`/`notification_log`.
- **topik-ai 소유**: admin 운영 schema — `notification_templates`, `notification_groups`, `notification_dispatches`, `notification_delivery_attempts`, admin RPC.
- **공유 객체**: 양쪽에서 읽거나 쓰는 객체(예: delivery_attempts를 v13 X-09가 읽음)는 **decision record로 owner / writer / reader / RLS / migration home을 명시**한다.
- 기존 v13 테이블 변경은 owner(v13) 승인 + migration decision record 필수.

선행 개정 대상 (Phase 0 첫 작업, 양 repo 오너 승인 필요):

1. v13 `AGENTS.md`의 "admin-oriented schema/migration 추가 금지" 문구를 도메인 소유권 모델로 완화.
2. topik-ai `AGENTS.md`의 `topik_writing_*` 한정 소유 범위를 admin 운영 네임스페이스(알림 포함)로 확장.
3. `docs/architecture/admin-data-source-transition.md` 스키마 소유권 절 개정.
4. 신규 SoT: `docs/architecture/shared-supabase-schema-ownership.md` (owner/writer/reader/RLS/migration home 매트릭스).

### 5.1 채널 계약 (4종, 의미 고정)

```ts
type NotificationChannel = 'in_app' | 'email' | 'push' | 'zalo';
```

| 채널 | 의미 | 상태 |
| --- | --- | --- |
| `in_app` | 앱 내부 알림센터·홈 카드·읽음/미읽음 | **1차 출시 채널** (provider 불필요) |
| `email` | 메일 발송 | 2차 (Phase 3, provider O-1) |
| `push` | OS/브라우저/앱 푸시 | **준비 중** — provider 없는 동안 발송 비활성. 기존 의미 유지 |
| `zalo` | 외부 메신저 | deferred (기존 정책 유지) |

**기존 `push`를 `in_app`으로 재해석하지 않는다** (rev2 O-4 철회). 관리자 UI 매핑:

- `/messages/mail` → DB channel `email`
- `/messages/push` → DB channel `push` — provider 연동 전까지 발송 버튼 비활성 + "준비 중" 표시
- `/messages/in-app` (신규 route 또는 message 내부 탭) → DB channel `in_app`

### 5.2 데이터 모델 — 발송 이력 3계층

발송 이력을 "템플릿 → 발송 실행(dispatch) → 수신자×채널 전달 시도(attempt)"로 분리한다. 관리자 이력 화면의 SoT는 dispatch+attempt이며, `notification_log`는 SoT로 쓰지 않는다.

| 테이블 | 소유 | 용도 | 핵심 컬럼 |
| --- | --- | --- | --- |
| `notification_templates` | topik-ai | 템플릿 원본 | `template_key`(unique), `class`(§4.1, **필수**), `mandatory boolean`(marketing은 true 저장 차단 CHECK), `channel`, `name`, `category`, `subject`, `body_html`, `body_json`, `variables jsonb`, `mode(auto/manual)`, `trigger_key`, `status`, `updated_by`, `updated_at` |
| `notification_groups` | topik-ai | 발송 대상 그룹 | `id`, `name`, `definition_type`, `filters jsonb`, `query_config jsonb`, `static_member_ids`, `status`, `updated_by` |
| `notification_dispatches` | topik-ai | **발송 실행 단위** (관리자 1회 발송 또는 스케줄러 1슬롯 실행) | `id`, `template_id`, `template_key`, `channels`, `target_type(group/schedule/event/test)`, `target_group_id`, `target_snapshot jsonb`, `recipient_count`, `status(draft/scheduled/running/completed/partial_failed/failed/canceled)`, `actor_id`, `reason`, `dedupe_key`(unique — 슬롯/캠페인 단위 재실행 방지), `scheduled_at`, `started_at`, `completed_at`, `created_at` |
| `notification_delivery_attempts` | topik-ai (v13이 read — 공유 decision record 대상) | **수신자×채널 전달 결과** | `id`, `dispatch_id`, `user_id`, `channel`, `status(pending/sent/failed/skipped/opted_out/deduped)`, `dedupe_key`(nullable, unique when present — 사용자×유형×회차 단위 중복 방지), `provider_message_id`, `error_code`, `error_message`, `sent_at`, `created_at` + unique(`dispatch_id`,`user_id`,`channel`) |
| `user_notifications` | **v13** | 인앱 수신함 표시 전용 | `id`, `user_id`, `template_key`, `category`, `title`, `body`, `link_url`, `payload jsonb`, `read_at`(읽음 상태는 **여기에만** 둔다 — attempt와 이중 상태 금지), `delivery_attempt_id`(역참조), `created_at` |
| `notification_log` | v13 (기존) | **deprecated** — 변경·사용하지 않음. X-09 이력 패널 데이터 소스를 attempts(owner-select RLS)로 교체 (O-9) | 변경 없음 |

- RLS: templates/groups/dispatches는 admin 전용(RPC write, service role read). attempts는 service role write + `user_id = auth.uid()` owner select(X-09 패널용) + admin read. user_notifications는 owner select + `read_at`만 owner update, insert는 service role.
- idempotency 2단: ① dispatch.dedupe_key (예: `sched:study_reminder:{슬롯 윈도우}`, `admin:{발송실행 id}`) ② attempt.dedupe_key (예: `{user_id}:study_reminder:{현지 날짜}`) — 윈도우 경계를 넘는 재처리에서도 사용자 단위 중복을 차단한다.

### 5.3 발송 파이프라인

```
[스케줄형] pg_cron (5~15분)
   → Edge Function `dispatch-notifications`
      1. dispatch 생성 (target_type='schedule', dedupe_key=슬롯 윈도우) — 이미 있으면 종료
      2. timezone 보정으로 슬롯 해당 사용자 산정
      3. class 정책(§4.1) + prefs + channels 평가
         → 제외자는 attempt를 skipped/opted_out으로 기록
      4. 템플릿 렌더링 → 채널별 발송:
         in_app → user_notifications insert (+attempt sent)
         email  → provider 호출 (+attempt sent/failed)
      5. dispatch status 집계 갱신 (completed/partial_failed/...)

[트리거형] 첨삭 완료 등 도메인 이벤트 (v13 서버)
   → 동일 Edge Function (target_type='event', 이벤트 id 기반 dedupe_key)

[관리자 수동] topik-ai 발송 실행
   → admin RPC `admin_send_notification(template_id, group_ids, scheduled_at?)`
   → dispatch 생성(draft→scheduled/running), 즉시면 Edge Function 호출, 예약이면 cron이 집행
   → mandatory 템플릿이면 bypass_reason 필수 → admin_audit_logs 기록
   → marketing은 수신 동의(O-7) 추가 평가
```

- service role key·provider secret은 Edge Function 환경변수에만 둔다.
- 실패 attempt는 cron 다음 회차에 최대 3회 재시도, 이후 종료 상태 고정.

## 6. 사용자 화면 계획 (v13)

### 6.1 X-09 알림 설정 보완

- 기존 화면 유지. 발송 시작 후 "발송 준비 중" 안내를 채널별 상태 표시로 교체.
- **발송 이력 패널 데이터 소스 교체**: `notification_log` → `notification_delivery_attempts` owner-select (O-9). 표시 계약(최근 5건, 빈 상태 정상)은 유지.
- 인앱 채널 토글 추가: `channels.in_app` (missing=true 해석, §4.3).
- 조건 토글 확장: O-8 결정에 따라 operational 계열 토글 노출. 와이어프레임 "토글 3개 키만 사용" 제약 문서 갱신.

### 6.2 인앱 알림센터 신설

- 헤더 벨 아이콘 + 미읽음 뱃지(99+ 상한), 드롭다운 수신함(최신순, 읽음/모두 읽음, `read_at` 기록 후 `link_url` 이동).
- 데이터: `user_notifications` owner select / `read_at` update. 미읽음 수는 폴링으로 시작(Realtime은 백로그).
- 빈 상태·로드 실패 상태 처리.

### 6.3 B-01 홈 대시보드 일정/알림 보조 영역

- `user_notifications` 최신 5건 카드 (와이어프레임 제약: 5개 이하, 로케일 날짜).
- `category` 구분 표시, 카드 클릭 → `link_url`, 설정 진입 → X-09, 로드 실패 → 재시도+설정 CTA.

## 10. 비범위 (Out of Scope)

- push 실제 발송 (provider 연동 전까지 "준비 중"), Zalo 실제 발송
- SMS, 마케팅 캠페인 고도화(A/B, 퍼널)
- 게시판(공지/이벤트) 화면 자체 — 알림 채널로의 전달만 이번 범위
- 사용자 timezone 편집 UI

## 11. 수용 기준 (전체)

1. 사용자가 X-09에서 설정한 주기·시간에 인앱 알림이 **중복 없이** 도착하고, 벨 뱃지·수신함·읽음·B-01 카드가 동작한다.
2. 관리자 발송 실행이 dispatch로 기록되고, 수신자별 전달 결과(sent/failed/skipped/opted_out)가 상세에서 확인되며, `admin_audit_logs`에 근거가 남는다.
3. **§8.3 E2E(관리자 직접 발송 → 사용자 수신 확인, mandatory bypass 포함 13단계)가 전 단계 통과하고 증적이 기록되어 있다.**
4. learning/marketing opt-out 사용자에게 attempt가 `sent`로 생성되지 않고, 제외자는 `skipped`/`opted_out`으로 집계된다. transactional/mandatory operational 우회는 class·mandatory·bypass_reason·actor 감사 기록과 함께만 가능하다. marketing 템플릿은 mandatory로 저장할 수 없다.
5. 발송 실패가 `failed`로 기록되고 재시도(≤3회) 정책이 동작한다.
6. §4.2 유형 6종이 template_key·class·category 계약으로 코드와 문서에 일관 반영되어 있다.
7. 기존 v13 테이블 DDL 변경 0건이 유지되고, 알림/admin migration은 `admin_schema_migrations`로 추적된다.
8. "저장됨"과 "발송됨"의 구분 표현이 유지된다 (push/zalo는 "준비 중").
9. service role key·provider secret이 클라이언트 번들에 포함되지 않는다.
10. 각 게이트(V-0~V-6) 통과 증적이 `logs/notification-feature-evidence.md`에 남아 있다.
