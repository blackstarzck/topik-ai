# TOPIK 쓰기 문항 버전·사용자 노출 운영정책

## 1. 문서 목적과 위상

- 이 문서는 `POL-017 TOPIK 쓰기 문항 수신·관리 운영정책` 중 **문항 수정 이력, 현재 버전, 사용자 상태별 노출 버전**을 정의하는 도메인 SoT다.
- 적용 대상은 관리자 `topik-ai`, 사용자 서비스 `v13`, 두 앱이 함께 사용하는 Supabase 문항·풀이 계약이다.
- 페이지 IA, 데이터 계약, 마이그레이션, RPC, 사용자 화면 구현이 이 문서와 다르면 이 정책을 기준으로 차이를 기록하고 정렬한다.
- 정책 확정일: 2026-07-15
- 현재 단계에서는 사용자에게 문항 버전 번호, 변경 이력, 변경 공지 또는 알림을 노출하지 않는다.

## 2. 핵심 결정

1. `question_id`는 수정 전후에도 유지되는 **논리 문항 식별자**다.
2. 외부 공급처에서 같은 `question_id`가 들어오면 `updated_at`과 실제 학습·채점 내용의 `content_hash`를 함께 비교한다. `updated_at`이 더 최신이고 `content_hash`가 달라진 경우에만 기존 데이터를 삭제하지 않고 **불변 버전**을 추가한다.
3. 관리자는 최신 버전과 과거 버전 이력을 조회할 수 있다.
4. 사용자에게 새로 노출되는 문항과 아직 제출하지 않은 상태는 항상 최신 버전을 따른다.
5. 버전을 영구 고정하는 시점은 문항 열람, 북마크, 임시저장이 아니라 **제출이 서버에서 확정된 시점**이다.
6. 제출 완료 데이터, 채점, 피드백, 과거 결과는 제출 당시 문항 버전과 스냅샷을 계속 사용한다.

## 3. 용어

| 용어 | 정의 |
| --- | --- |
| 논리 문항 | 수정 전후를 하나의 문제로 묶는 `question_id` 단위 |
| 문항 버전 | 특정 시점에 수신된 불변 문항 payload. `canonical_import_id` 또는 동등한 import ID와 `payload_hash`로 식별 |
| 현재 버전 | 해당 `question_id`에서 신규 풀이·북마크·임시저장에 사용되는 최신 활성 버전 |
| 원본 생성 시각 | 공급 API의 `created_at`. 같은 `question_id`에서 바뀌지 않는 문항군 기준선 |
| 원본 수정 시각 | 공급 API의 `updated_at`. UTC ISO-8601이며 공급처 수정 순서를 판정하는 값. 내부 버전 ID로 사용하지 않음 |
| 원문 해시 | `payload_hash`. 시각·메타데이터까지 포함한 원본 응답 전체의 무손실 중복 수신 식별값 |
| 내용 해시 | `content_hash`. 식별자·수신/원본 시각·운영/검수 메타데이터를 제외한 학습·채점 canonical projection의 해시 |
| 미제출 상태 | 사용자가 제출을 완료하지 않은 북마크 또는 임시저장 상태 |
| 제출 스냅샷 | 제출 확정 시점의 사용자 노출용 문항 본문·자료·질문·채점 맥락을 변경 불가능하게 저장한 값 |

## 4. 상태별 버전 적용 규칙

| 상태/화면 | 적용 버전 | 버전 고정 여부 | 문항 수정 후 동작 |
| --- | --- | --- | --- |
| 관리자 현재 문항 목록·상세 | 현재 버전 | 아니요 | 최신 버전을 기본 표시 |
| 관리자 버전 이력 | 승격된 모든 불변 버전 | 예 | 버전별 수신 시각, import ID/hash, 현재 여부와 해당 버전 전체 내용을 조회. 자동 필드 diff는 후속 범위 |
| 신규 문제 목록·새 풀이 | 현재 버전 | 아니요 | 수정된 최신 버전을 표시 |
| 북마크 | `question_id`의 현재 버전 | 아니요 | 북마크 관계는 유지하고 열람 시 수정된 최신 버전을 표시 |
| 임시저장 | `question_id`의 현재 버전 + 기존 임시답안 | 아니요 | 답안은 보존하되 재진입 시 수정된 최신 문항을 표시 |
| 제출 요청 처리 중 | 서버가 확정한 현재 버전 | 제출 성공과 동시에 고정 | 클라이언트가 열었던 시점이 아니라 서버 제출 확정 시점의 버전을 스냅샷으로 저장 |
| 제출 완료·채점·피드백·과거 결과 | 제출 스냅샷 | 예 | 이후 최신 버전이 바뀌어도 제출 당시 문항을 유지 |
| 다시 풀기·새 시도 | 현재 버전 | 새 제출 시 다시 고정 | 과거 제출은 보존하고 새 시도에는 최신 버전을 사용 |

“푼 문제”라는 표현은 단순 열람이나 임시저장을 포함하지 않는다. 이 정책에서 과거 버전을 유지하는 사용자 데이터는 **제출이 성공한 풀이**를 의미한다.

## 5. 임시저장 안전 규칙

- 임시저장은 과거 문항 버전을 사용자에게 계속 보여주는 근거가 아니다. 북마크와 마찬가지로 논리 문항 `question_id`를 따라 최신 버전을 조회한다.
- 문항 버전이 바뀌어도 사용자가 작성한 임시답안을 자동 삭제하지 않는다.
- 재진입 또는 제출 직전에 최신 문항과 임시답안을 다시 결합하고, 문항 유형·입력 구조·필수 자료·답안 형식의 호환성을 검증한다.
- 호환되는 변경이면 기존 답안을 유지한 채 최신 문항으로 계속 진행하고, 제출 성공 시 최신 버전을 고정한다.
- 호환되지 않는 변경이면 조용히 잘못된 답안을 제출시키지 않는다. 제출을 중단하고 사용자가 최신 문항과 답안을 다시 확인할 수 있는 복구 경로를 제공한다.
- 일반적인 문항 수정에 대해 별도 공지, 푸시, 버전 배지 또는 변경 이력을 사용자에게 제공하지 않는다. 호환성 실패 안내는 제출 정합성을 지키기 위한 인라인 오류 처리이며 일반 변경 알림으로 보지 않는다.

## 6. 같은 `question_id`를 유지할 수 있는 수정 범위

- 오탈자, 표현 명확화, 사실관계 교정, 자료 표시 보정처럼 **같은 학습 과제와 답변 의도**를 유지하는 수정은 새 버전으로 저장하되 같은 `question_id`를 유지할 수 있다.
- 요구 과제, 핵심 상황, 답안 형식, 평가 목표가 달라져 사실상 다른 문제로 바뀌는 수정은 같은 `question_id`의 새 버전으로 처리하지 않는다. 새 `question_id`를 발급한다.
- 이 경계를 지키지 않으면 임시답안이 최신 문항과 의미상 충돌하므로, 외부 수신 검증 또는 관리자 이력 확인 과정에서 식별자 재사용 오류를 탐지해야 한다.

## 7. 관리자 문항 관리 규칙

- 한 응답에는 같은 `question_id`가 한 번만 존재해야 하며, `created_at`은 같은 문항군에서 불변이고 `updated_at >= created_at`이어야 한다.
- 동일 `payload_hash` 재수신은 새 행을 만들지 않고 재수신 횟수와 마지막 수신 시각만 갱신한다.
- 더 최신 `updated_at`과 다른 `content_hash`가 함께 확인된 경우에만 `content_changed` 불변 버전을 추가하고 승격 후보로 둔다. 내용 비교 기준은 가장 최신의 유효한 수신본(`promoted` 또는 검수 완료 수신)이며, 서비스 현재 버전 판별은 계속 canonical 포인터만 사용한다. 따라서 승격 재시도 전에 같은 내용이 더 최신 시각으로 다시 수신돼도 중복 내용 버전을 만들지 않고, 과거 내용으로 되돌린 수정은 직전 유효 수신과 내용이 다르고 시각이 더 최신이면 새 버전이 된다.
- 더 최신 `updated_at`이지만 `content_hash`가 같으면 `metadata_only` 수신 행으로 보존하되 수정 횟수와 현재 포인터를 바꾸지 않는다.
- 같거나 과거인 `updated_at`에 내용이 다르면 `timestamp_conflict`/`out_of_order`, 문항군의 `created_at`·번호가 다르면 `identity_conflict`, 시각이 없거나 잘못됐으면 `invalid_timestamp`로 보류한다.
- `metadata_only`와 이상 응답은 인박스에서 상태·사유를 확인하며 문항관리의 승격 버전 수에는 포함하지 않는다.
- 번호별 현재 문항 테이블을 upsert하더라도 이는 최신 조회용 projection으로만 취급한다. 버전 이력의 SoT는 불변 import 버전과 현재 버전 포인터다.
- `service_status`, 태그, 기관 노출처럼 관리자가 소유하는 운영 값은 외부 문항 내용 버전과 분리해 유지한다. 외부 수정 수신만으로 운영 값이 초기화되어서는 안 된다.
- 관리자는 버전 순서, 원본 생성/수정 시각, 수신 시각, import ID, payload/content hash, 현재 버전 여부와 해당 버전 전체 내용을 조회할 수 있어야 한다. `raw`·`held` 인박스 행은 문항관리 이력에서 제외하고 가져온 문항 인박스에서 확인한다.
- 이전 버전 대비 자동 필드 diff는 이력 1차 UI 범위에 포함하지 않으며 후속 갭으로 추적한다.
- 과거 버전 복원과 임의 재활성화는 현재 정책 범위가 아니다. 해당 기능을 도입하려면 별도 확인 절차와 감사 액션을 먼저 확정한다.

## 8. 감사 로그 규칙

- 문항 수신과 현재 버전 전환은 `Target Type = AssessmentQuestion`, `Target ID = question_id`로 추적한다.
- 기존 `question_received` 액션에는 최소한 import ID, payload/content hash, 원본 생성/수정 시각, `version_decision`, 신규 버전 생성 여부와 현재 버전 전환 여부를 기록한다.
- 동일 payload 재수신은 문항 내용 변경으로 기록하지 않는다.
- 사용자 제출 스냅샷 생성은 사용자 도메인 쓰기이며 관리자 조치 감사 로그 대상이 아니다. 제출 원장과 서버 로그에서 추적한다.

## 9. 데이터 소유권과 앱 경계

| 객체/책임 | 소유 저장소 | 규칙 |
| --- | --- | --- |
| `topik_writing_question_import`, 현재 버전 포인터, 번호별 현재 문항 projection | `topik-ai` | 불변 버전 생성, 최신 전환, 관리자 이력 제공 |
| `service_status`, 문항 태그, 기관 노출 | `topik-ai` | 문항 내용 버전과 분리된 관리자 운영 값 |
| 북마크·임시저장 | `v13` | `question_id` 기준으로 최신 버전 해석. 과거 버전을 사용자 노출용으로 고정하지 않음 |
| `writing_submissions`, 제출 문항 스냅샷, 채점·피드백 이력 | `v13` | 제출 확정 시점 버전을 불변으로 고정 |

- `topik_writing_*` DDL은 `topik-ai`의 `supabase/migrations/`가 소유한다.
- `writing_drafts`, `writing_submissions`와 사용자 상태 DDL은 `v13`이 소유한다.
- 한 저장소의 마이그레이션에서 다른 저장소 소유 테이블의 DDL을 변경하지 않는다.

## 10. 예외와 노출 중단

- 최신 문항의 `service_status`가 `available`이 아니면 신규 풀이와 북마크 열람에서 과거 버전으로 자동 대체하지 않는다.
- 미제출 임시저장은 보존할 수 있으나, 최신 문항이 제출 가능 상태가 될 때까지 제출을 허용하지 않는다.
- 이미 제출한 결과는 현재 문항의 노출 상태가 바뀌어도 제출 스냅샷을 기준으로 유지한다. 법률·보안·개인정보 사유로 과거 결과까지 차단해야 하는 경우에는 이 정책이 아닌 별도 강제 비노출 정책과 감사 근거가 필요하다.

## 11. 필수 검증 시나리오

1. 동일 payload 재수신 시 버전이 중복 생성되지 않고 수신 횟수만 증가한다.
2. 더 최신 `updated_at`과 변경된 `content_hash`가 함께 온 경우 기존 버전이 남고 새 버전이 현재 버전이 된다.
3. `updated_at`만 변경된 응답은 `metadata_only`로 보존되고 버전 수와 현재 포인터가 바뀌지 않는다.
4. 과거/동일/잘못된 시각 또는 문항군 식별 충돌은 보류되고 현재 포인터가 바뀌지 않는다.
5. 수정 전에 생성한 북마크를 열면 최신 문항이 표시된다.
6. 수정 전에 작성한 임시답안은 보존되며, 재진입 시 최신 문항이 표시된다.
7. 임시답안과 최신 문항이 호환되지 않으면 제출이 차단되고 복구 경로가 표시된다.
8. 제출 성공 시 서버가 사용한 import ID, payload hash, 문항 스냅샷이 함께 고정된다.
9. 제출 후 문항이 수정되어도 채점·피드백·과거 결과에는 제출 당시 문항이 표시된다.
10. 다시 풀기에서는 최신 문항을 사용하고 과거 제출 결과는 바뀌지 않는다.
11. 외부 수정 수신 후에도 `service_status`, 태그, 기관 노출 값이 보존된다.

## 12. 구현 상태 해석

- 이 문서는 확정된 운영·정책 SoT이며, 현재 코드가 모든 항목을 구현했다는 의미는 아니다.
- `topik-ai`의 현재 버전 포인터는 `topik_writing_question_source_map.canonical_import_id`로 구현돼 있으며, 인박스 `is_latest`를 현재 버전 판별에 사용하지 않는다.
- 관리자 버전 이력 1차 구현은 `/assessment/question-bank`의 수정 횟수·확장 이력과 `/assessment/question-bank/:questionId`의 현재/과거 버전 탭·과거 payload 상세 조회를 제공한다. 이력에는 원본 생성/수정 시각과 content hash를 함께 표시하며, 집계는 성공적으로 승격된 버전만 대상으로 하고 `raw`·`held`는 제외한다.
- `topik-ai`에는 `source_created_at`/`source_updated_at`/`content_hash`/`version_decision`, 문항별 advisory lock, 50건 단위 적재·승격을 구현했다. 2026-07-16 사전 점검에서 공급 API 701건의 `updated_at`이 모두 null이라 마이그레이션 적용을 보류했으나, 공급처가 `updated_at`을 채우기로 확정(2026-08-24 오너 결정)되어 dev·운영에 적용했다. 기존 행은 `coalesce(updated_at, created_at)` 백필로 `version_decision='legacy'`가 되고 canonical 포인터는 불변이다. 공급처가 실제로 채우기 전(갭 구간)의 신규 수신은 `invalid_timestamp` held로 인박스에 보존되며, 채워지면 `payload_hash`가 바뀌어 새 행으로 정상 승격된다.
- `v13` 운영 코드·스키마는 변경하지 않는다. 현재 구현의 canonical import/hash 충돌 가드와 제출 `question_snapshot`/`legacy_cutover_snapshot` 관련 단위·마이그레이션 테스트 65건은 통과했다. `metadata_only` 비승격과 실제 내용 변경 승격을 연결한 live 교차 E2E는 공급 `updated_at` 계약과 guarded 실행 환경이 준비된 뒤 수행한다.
- 관리자 이력은 조회 전용이다. 과거 버전 복원·재활성화와 이전 버전 대비 자동 필드 diff는 구현하지 않았으며 후속 갭으로 유지한다.
- `v13`의 북마크·활성 임시저장 최신화, 제출 충돌 차단, 완료 제출 스냅샷은 기존 구현을 유지하며 신규 production 변경 없이 교차 저장소 검증만 보강한다.
- 남은 외부 선행 조건과 live 교차 검증 차이는 `docs/specs/admin-page-gap-register.md`에서 추적한다.
